# ViT J1-J2 Heisenberg NQS — Progress Summary (week of Jul 21–28, 2026)

## TL;DR

Ran a full 96-job J2 sweep (0.1 → 2.0) with proper seed statistics on the ViT neural quantum state,
found and fixed two real correctness bugs along the way (a GPU-sizing OOM and a NaN-detection bug),
generalized the training script (new spin sectors, Hamiltonians, linear solvers), and found that the
ansatz reliably failed to converge above `J2≈1.3` with the hyperparameters we had been using. Standard
hyperparameter tuning resolved most of it: the SR diagonal shift we were running (`1e-4`) was simply
too small for this ansatz in the frustrated regime, and `1e-3` took `J2` 1.3–2.0 from 1/32 to 27/32
converged. No new methodology here — the high-`J2` range is now usable, which unblocks doing physics
with it.

## 1. Full J2 sweep at L=10, J2 = 0.1 → 2.0

- 96 jobs: `J2` at 0.1 spacing across the full range (plus extra 0.05-spacing points through the
  0.3–0.7 Neel-stripe crossover) × 4 seeds, `n-iter=3000` each.
- **Bug #1 — GPU out-of-memory:** the `.slurm` script's default GPU allocation (`gpu:1g.10gb:1`, a
  ~9.5GB MIG slice) wasn't enough memory for the stochastic-reconfiguration step at the default
  sampler settings. All 96 jobs failed immediately on the first attempt. Fixed by making
  `gpu:3g.40gb:1` the permanent default.
- Worked around the cluster's 40-job-per-user submission cap with a small detached "drip-feed" daemon
  that submits more jobs as slots free up.
- **Result:** 60/96 converged cleanly, 32/96 were caught and stopped early by the divergence guard,
  4/96 silently went to NaN (see Bug #2). Energy-per-site tracks the expected physics through the
  `J2≈0.5` crossover, but **the ansatz essentially never converges for `J2≥1.5`** with default
  hyperparameters — see `j2-sweep-L10/j2-sweep-summary.png`.

## 2. Bug #2 — divergence guard didn't catch NaN

The divergence guard checked `abs(energy) > threshold` — but NaN comparisons are always `False` in
Python/numpy, so a run that went to NaN sailed straight past the guard and burned its full ~9.8h GPU
allocation logging garbage instead of stopping early. This happened to 4 of the 96 sweep runs. Fixed
with an explicit `math.isnan(...)` check.

## 3. Training-script generalization (`netket-vit.py`)

Added, each verified with regression + smoke tests:

- `--total-sz` — fixed magnetization sector (default, unchanged) or `"none"` for an unrestricted
  Hilbert space, with the Monte Carlo sampler automatically switched (`MetropolisExchange` ↔
  `MetropolisLocal`) to match, since the exchange sampler can't explore multiple sectors.
- `--model {heisenberg,xy,ising}` — alternate spin couplings, built by hand from the lattice's colored
  bonds and cross-validated to reproduce the built-in Heisenberg operator exactly.
- `--field` — a longitudinal (Zeeman) term, with a guard against the physically-meaningless case of
  combining it with a fixed `total_sz` sector (caught a real conceptual bug here before it shipped).
- `--linear-solver {cholesky_with_fallback,cholesky,pinv_smooth}` — exposes NetKet's own recommended
  lever for the NaN-blowup problem.
- Fixed a filename-collision bug: `run_name` now encodes `--learning-rate`/`--diag-shift` when
  non-default, so differently-tuned runs at the same `(J2, seed)` no longer silently overwrite each
  other's output.

## 4. Documentation pass

Added extensive physics-first comments/docstrings throughout `vit_model.py`, `netket-vit.py`, and

## 5. Hyperparameter tuning to make `J2≥1.3` tractable

*Nothing novel in this section — it is routine tuning of an existing, standard knob, recorded because
it is what unblocked the high-`J2` range.* The diagonal shift is ordinary Tikhonov/ridge
regularization of the quantum geometric tensor (solving `(S + λI)x = f` rather than `Sx = f`, since the
Monte-Carlo-estimated `S` is noisy and near-singular). It has been part of stochastic reconfiguration
since Sorella's original work and is a first-class parameter in NetKet's API (`VMC_SR(diag_shift=…)`,
which also accepts a decaying schedule). We were already setting it; we only changed its value.

A 30-job probe tested whether a different linear solver, a larger `diag-shift`, or a smaller learning
rate would let `J2 ∈ {1.3, 1.6, 2.0}` converge. Results: `--diag-shift 1e-3` and
`--learning-rate 0.003` each survived 6/6, our previous setting 0/6. Notably `pinv_smooth` — NetKet's
own documented suggestion for NaN blow-ups — scored only 1/6, so what mattered was more SR
regularization or a smaller step, not a better linear solve. That is a mildly useful practitioner's
note for anyone hitting the same symptom, not a finding.

`--diag-shift 1e-3` was then used for a full `n-iter=3000` rerun of `J2` = 1.3–2.0 × 4 seeds (32 jobs):
**27/32 converged, versus 1/32 at `1e-4`.** Per `J2` (converged/4, energy/site):
1.3 → 3/4 (-0.891), 1.4 → 4/4 (-0.957), 1.5 → 4/4 (-1.024), 1.6 → 3/4 (-1.089), 1.7 → 3/4 (-1.157),
1.8 → 4/4 (-1.224), 1.9 → 4/4 (-1.291), 2.0 → 2/4 (-1.358). Seed-to-seed agreement within a `J2` is
typically 4+ decimal places and energy/site falls smoothly and monotonically with `J2` — both good
signs the converged values are sound. Residual failures are scattered, with no single consistently
unstable seed and no clean `J2` threshold.

A second 16-job probe at `J2 ∈ {1.7, 2.0}` tested stronger settings (`diag-shift` 3e-3 and 1e-2, each
alone and combined with `lr 0.003`) against the specific cases that failed under 1e-3. Every config
tested rescued them, including `J2=1.7` seed 2 (which had died at step 308) and `J2=2.0` seed 0 (step
2904). The lower `diag-shift` still gives the best energy wherever it survives, so there is a real
stability-vs-accuracy tradeoff in choosing a default.

Two methodology lessons came out of this:

- **A short stability probe can give a false positive.** The 500-iteration probe scored `diag-shift
  1e-3` as 6/6 at `J2`=1.6/2.0, but at full length runs there still diverge — as late as step 2904. A
  probe must run past where the current best config already fails, or it measures "how long until it
  breaks" rather than "does it break."
- **Never classify a run by log length while it is still running.** An early pass treated any log with
  fewer than 3000 iterations as diverged, which mislabeled every in-flight job as a failure and
  produced a badly wrong summary table. Ground truth is the `Diverging:` line in the job's stdout,
  cross-checked against `sacct` completion state.

## 6. Library-vs-extend decision

Weighed building a custom NetKet-like library against extending NetKet's public API — recommended
against a from-scratch library: too much subtle numerical-correctness surface to re-derive (complex
autodiff, QGT/SR linear algebra, MCMC autocorrelation, stable solvers), where bugs don't crash but
silently yield plausible-looking wrong physics. The ansatz, not the VMC/QGT machinery, is where this
project's novelty lives, and every gap hit this week was closable by extending the public API.
